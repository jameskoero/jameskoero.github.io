Validating an ONNX export

Nyando Flood AI: when the standard converter was silently wrong

Case studiesResearchWritingExperienceSkillsAboutCV

Last updated: 18 Nov 2026

Result

The served model is exported by a custom ONNX writer. It reproduces scikit-learn to a largest difference of 3.3e-16 on the 27 sealed events and 2.5e-16 on the training rows, with a per-event AUC difference of 0 and zero monotonicity violations. The standard converter produced differences up to 0.981.

What went wrong with the standard converter

  • skl2onnx 1.20.0 with onnx 1.23.2 failed on every HistGradientBoosting model: it passed a boolean where ONNX expects an integer.
  • With that cast by hand, it exported without error but ignored scikit-learn's internal column order and had no category splits.
  • The result ran and looked valid but was wrong: differences up to 0.981, and the monotonic constraints broken in the exported file.

A model that fails loudly is safe. One that exports silently wrong is the dangerous case, and only a parity test on real rows catches it.

The fix

  • A custom writer builds one ai.onnx.ml TreeEnsemble node (opset 5, IR 10, double precision) from the fitted trees: 100 trees, 1,013 nodes, 1,113 leaves.
  • It follows the production input contract of the API, so the exported file sees exactly what the service sends.

In production

The FastAPI service checks the model file's SHA-256 before loading it and refuses a file that does not match. The registered file is nyando_hgbcon_5ae81ad8b030.onnx, served with onnxruntime 1.30.0.

Limits

The writer covers the model types used in this project. It is not a general replacement for skl2onnx, and the converter faults are described for the versions named above only.
