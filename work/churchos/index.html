ChurchOS

Multi-tenant church management software

Status: Live, version 3.4.0  |  Last updated: 18 Nov 2026

Problem

Churches need one system for members, giving and records, with each church's data kept separate. ChurchOS is a multi-tenant product: one platform, many separate churches.

Requirements

  • Keep each church's data separate from every other church's.
  • Control access by role, with five roles.
  • Record finance actions in an audit log.
  • Take giving by M-Pesa.
  • Keep working when the connection drops, and protect member data, which includes religious belief.

Architecture

Implementation

Version 3.4.0 is live. It was built in 28 numbered fix packs, merged through 21 pull requests.

  • JWT sign-in and five roles: admin, pastor, secretary, treasurer and viewer.
  • Each church's data kept separate from every other church's, with a finance audit log.
  • M-Pesa giving through Safaricom Daraja, with a setup check, receiving accounts and statement import.
  • Reports, and encrypted nightly database backups run by GitHub Actions.
  • Billing, plans and invoices for churches that use the platform.
  • Offline attendance that syncs when the connection returns.
  • SMS through Africa's Talking, sent only with consent and with STOP handling.
  • Denomination structure and regions, so a region can see its altars together.
  • Privacy and terms pages, a request form and an uptime check.

Design decisions

  • Each church can connect its own M-Pesa, so giving goes straight to the church and not through the platform. Its keys are stored encrypted. This ships switched off until a church is ready.
  • Sign-in by SMS code is built and also ships switched off, with a setting that turns it off for everyone in an emergency.
  • Each church picks its denomination, and the product follows that denomination's structure.

Evaluation

  • 192 automated tests in 26 files cover separation between churches, money, payments, sign-in, SMS, billing and the newer features.
  • GitHub Actions runs the backend tests and the frontend build on every pull request; the last four pull requests passed all four checks.
  • The live server reports its version at /api/health, which answered 3.4.0 on 14 Nov 2026.

My contribution

I designed, built and deployed the product as the sole developer.

Results and limitations

  • Version 3.4.0 is live, with billing, SMS and offline attendance built.
  • The API runs on Render's free plan, so the first request after a quiet period is slow while it wakes.
  • Live SMS and each church's own M-Pesa need accounts and settings before they are switched on.
  • No usage figures are published here.

What I would do next

  • Switch on live SMS and a church's own M-Pesa for a first church, then trial SMS sign-in on a non-critical account.
  • Have an advocate review the privacy and terms pages before charging any church.
